# 为什么需要 RLS：从真实浪费出发

## 真实数据看到的浪费

对 33 个 AI 编程会话、11,560 次工具调用的分析：

| 工具 | 次数 | 占比 | Token |
| --- | --- | --- | --- |
| Bash | 4,391 | 38% | 4.4M |
| Read | 2,669 | 23% | 5.3M |
| Edit | 2,235 | 19% | 1.8M |
| Grep | 744 | 6% | 1.1M |

* Read + Grep 合计约 50% token（约 6.4M）。
* 典型浪费模式：**Grep → Read × N，出现 317 次**：先 grep 出一堆行，再一个个读文件补上下文。
* 语义/向量搜索只用了 2 次（0.9%）：贵、要部署、结果还不可核对。

结论：**先定位、再深读、按证据追踪**，比“全文读 + 猜”省得多。这就是 RLS 的设计起点。

## RLS 的取舍（故意的）

* 要：字面精确搜索（99% 场景够用、快、无依赖）+ AST 调用图（知道谁调谁）。
* 不要：向量库、embedding 模型、重排模型、云服务。本地单文件就能跑，不上传代码。
* 结果必须带：文件路径 + 行号 + 符号名 + 快照 ID，能回源码核对，不能是黑盒猜测。

## 一句话定位

> RLS 不是“更快的 grep”，是 **AI 读代码的导航仪**：先给地图和坐标，再按需深读。
